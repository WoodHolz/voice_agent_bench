# 首轮架构实验结果

已完成两个可运行 demo、共享数据、统一 benchmark 和逐步 ASR 模拟。**本次 CPU 配置下，semantic-router 更适合作为下一轮快速意图识别实验的起点；两者当前配置都不足以直接用于生产。** 这个判断针对本次模型和接入方式，不是对两个库所有部署配置的排名。

## 条件与覆盖

- 2026-09-09，本机 Intel Core i5-11320H，4 核/8 线程；推理配置 4 个 Torch 线程，CPU，无 GPU。硬件信息见 [hardware.txt](hardware.txt)。同一用户工作机，未控制后台负载。
- 两边共享 `paraphrase-multilingual-MiniLM-L12-v2`（384 维、归一化向量）；Demo A 另用 `mmarco-mMiniLMv2-L12-H384-v1` cross-encoder。模型 revision 固定于 config.yaml。
- 129 条索引例句；59 项产品定义中 58 项是文本意图。7-1 静默需外部事件，未伪造文本标签。
- 主评测 220 条，每个 router/mode 测一次，共 880 次调用；主准确率只计 116 条未加入索引的改写，每个意图两条。71 条产品原话诊断与 33 条 challenge 独立报告。
- 另测 8 条“真实授权提问上下文中的 OOD”，两个 router 共 16 次调用。该压力集在第一轮结果后补充，没有据此调模型、阈值或训练例句。
- ASR 模拟 4 条序列、18 个假设，两个 router 共 36 次 detect。
- 所有实测无后端错误。模型/索引加载独立记录，热请求延迟包含 embedding/检索/重排，不包含 ASR、TTS、HTTP、队列或后台摘要。

## 准确率与延迟

来自 [baseline.json](baseline.json) / [baseline.md](baseline.md)：

| Router | 输入/索引配置 | 留出集正确数 | Accuracy | p50 | p95 | p99 |
|---|---|---:|---:|---:|---:|---:|
| RealtimeIntent | 纯文本 | 19/116 | 16.4% | 165.4 ms | 218.2 ms | 265.0 ms |
| semantic-router | 纯文本 | 57/116 | 49.1% | 22.9 ms | 35.5 ms | 42.1 ms |
| RealtimeIntent | 带上一轮对话 | 20/116 | 17.2% | 189.1 ms | 252.1 ms | 280.8 ms |
| semantic-router | 带上一轮对话 | 83/116 | 71.6% | 28.9 ms | 46.6 ms | 57.1 ms |

分位数统计各配置的 218 次非空成功请求；准确率只统计 116 条 heldout，两个口径不可混淆。表中的 p99 是小样本统计值，不能视为线上 SLA。

RealtimeIntent 纯文本配置的正确标签召回率为 80/116（69.0%）；带上下文为 114/116（98.3%）。带上下文时，114 条已召回正确候选的样本中有 94 条在重排/拒识后未得到正确标签。因此当前问题主要集中于重排/拒识阶段，不能只靠增加检索候选解释。更换的通用小 reranker、描述形式、对话输入包装及上游阈值之间可能不匹配，尚未做消融验证因果。

这不是上游推荐的 Qwen Embedding/Reranker GPU 配置。没有依据将 17.2% 外推为“RealtimeIntent 算法上限”，也没有按测试集降低阈值掩盖问题。

## 相近意图与拒识

semantic-router 加上下文后有所改善，但存在关键混淆：

- 7-38 → 7-36：没收到被判为收到未填（2/2）。
- 7-41 → 7-40：查找后没有被判为找到（2/2）。
- 7-16 → 7-15：先核实被判为信任恢复（2/2）。
- 7-46 → 7-47：坚称全完成被判为疑似没提交（2/2）。

这些是语义/否定区分失败，不能交给分类器直接驱动业务动作。

同一句在不同上下文中的 8 条对照测试，两边带上下文均命中 5/8。纯文本歧义集合测试 semantic-router 命中 6/7，RealtimeIntent 命中 3/7；这只是可接受集合命中率，不等于唯一标签准确率。上下文索引遇到没有上下文的歧义输入表现会变化，不能混成一个“歧义准确率”。

| OOD 条件 | RealtimeIntent 拒识 | semantic-router 拒识 |
|---|---:|---:|
| 纯文本路由，8 条无关输入 | 5/8 | 8/8 |
| 上下文索引，但输入不提供上下文 | 4/8 | 8/8 |
| 上下文索引，输入含真实授权提问 | 3/8 | 2/8 |

最后一行来自 [context-ood.json](context-ood.json)。例如上一句问“授权通知收到了吗”，用户说“帮我写一个排序程序”，semantic-router 判为 7-37，余弦聚合分数约 0.895。这说明把上一轮问题拼进 embedding 会让上下文主导相似度；“纯 OOD 全拒识”并不意味着对话中也能可靠拒识。

RealtimeIntent 的 result.score 是本地 cross-encoder sigmoid 相关性；semantic-router 是召回例句余弦的 route 聚合分数。两者都不是已校准概率，数值不可横比。

## 增量 ASR 稳定性

来自 [stream.json](stream.json)，纯文本配置，没有去抖或提交门槛：

| 序列 | RealtimeIntent 预测变化次数 / 最终正确 | semantic-router 预测变化次数 / 最终正确 |
|---|---|---|
| 我 → 我刚才填错了能改吗 | 3 / 否 | 3 / 否 |
| 刷 → 刷脸一直过不了 | 3 / 否 | 3 / 是 |
| 不用 → 不用了别再打了 | 3 / 否 | 1 / 是 |
| 链接 → 链接打得开 → 链接打不开 → 完整故障描述 | 2 / 否 | 2 / 否 |

semantic-router 的人脸序列在最终 7 字时才持续正确；拒绝序列从“不用了”开始持续正确。两边在“我”“我刚”等不足以判定的片段上都有错误接受。RealtimeIntent 有些最终输入被拒识，变化次数少也不代表稳定正确。四条序列只能揭示问题，不能证明总体稳定性。

## 七个决策问题

1. **RealtimeIntent 能否可靠区分产品意图？** 当前本地小模型配置不能。需要在独立 dev 集适配重排模型、输入形式和阈值，或测其推荐 Qwen 服务，才能评价这条架构的潜力。
2. **semantic-router 能否可靠区分？** 带上下文达到 71.6%，但否定、邻近标签及对话中 OOD 仍有明显问题，尚不能视为可靠。
3. **哪个更低延迟？** 本次 semantic-router 的 p50/p95 均明显更低；只做一次 embedding+本地匹配，没有 Demo A 的重排推理。未测远端调用、并发或 GPU。
4. **哪个更稳定处理增量 ASR？** 本次 semantic-router 4 条中最终正确 2 条，RealtimeIntent 0 条；两者均有提前错误标签，不能直接消费每个 partial 去执行工作流。
5. **哪个更会处理相近/歧义意图？** semantic-router 在本次纯文本集合测试更好；带上下文同句测试两边相同，但仍有产品标签重叠及否定误判，无法作通用结论。
6. **需要多少配置/训练/例句？** 两边共享 129 例，无微调。Demo A 额外需要 58 项文本意图描述映射、__no_intent__ 描述、reranker 模型与拒识参数；Demo B 需要 route 例句、embedding、聚合方式和阈值。现有数据很小，不能估算达标所需样本量。
7. **哪个适合作为快速第一阶段？** 下一轮优先保留 semantic-router 作为低延迟基线，同时保留 RealtimeIntent 对照。当前都不能直接决定生产分支，尤其不能把 partial 的一次预测当作最终意图。

后续可在不改变产品流程的前提下，建立人工复核的独立 dev/测试集，验证最新发言与历史上下文的权重、独立阈值校准、拒识和相似意图区分。当前实验已提供测量工具，不实现这些后续策略，也不提前重设计 Workflow Policy。
